# Penguin 索引质量核验反馈

## 当前结论

本次 Q1–Q10 样本核验未发现明确的 Penguin 索引缺边或幻边。

不过，这个结果只能说明当前样本答案与源码基本匹配，不能直接推断整个仓库的索引质量已经完全正确。

## 建议

### 1. 将样本核验自动化

建议创建一个验证脚本，自动比较 Penguin 查询结果与 `rg` 或源码分析结果，并报告：

- 缺失边
- 多余边
- 仅存在于测试代码中的调用
- 仅存在于生产代码中的调用
- 缺失的函数、类、方法或类型声明

这样可以减少人工比较，也可以避免命令参数不兼容导致无效核验。

### 2. 明确测试代码是否计入调用者

Q2 和 Q3 的独立搜索结果包含 `.test.ts` 文件。建议在 benchmark 中明确区分：

- 生产代码调用者
- 测试代码调用者

两类结果都可以保留，但不应混合成一个调用者数量。

### 3. 为 Q5–Q7 增加关系置信度

这些问题涉及 hook、解构函数和推断关系。建议为每条边增加以下状态之一：

- 已确认的直接调用
- 通过 hook 确认的调用
- 推断关系
- 未确认

Penguin context 已经提示部分关系是 inferred，因此这些关系不应全部当作源码中直接存在的调用。

### 4. 生成机器可读的结果

建议同时生成 JSON 结果，例如：

```json
{
  "q1": {
    "status": "pass",
    "missing": [],
    "extra": []
  },
  "q2": {
    "status": "pass",
    "productionCallers": 1,
    "testCallers": 1
  }
}
```

这样可以把索引质量检查接入 CI，并在索引质量发生回退时及时发现。

### 5. 在核验前检查索引新鲜度

建议每次核验前确认：

- 当前仓库分支和 commit
- Penguin 实际索引的 commit
- 是否存在未提交修改
- 目标文件是否已经被索引
- 当前索引覆盖率是否完整

否则，即使查询结果正确，也可能只是旧版本代码的正确结果。

### 6. 分开发布质量结论

建议不要只输出一个总的“通过”结论，而是分别报告：

- caller/callee 正确性
- 文件符号完整性
- 测试覆盖情况
- 索引新鲜度
- CLI 与 MCP 结果一致性
- 仓库覆盖率

## 总体反馈

当前 answer key 很适合作为人工 benchmark。下一步最值得做的是把它转换成可重复执行的自动化回归测试。

目前的结果可以证明“这几组样本匹配”，但还不足以证明“Penguin 在整个仓库中都完全正确”。
